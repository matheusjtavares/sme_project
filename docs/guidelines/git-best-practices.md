# Version Control Best Practices (Git) — Guidelines

> Source: https://www.git-tower.com/learn/git/ebook/en/command-line/appendix/best-practices
> A summary in my own words of the guidelines on that page.

These are guidelines to help you get the most out of version control and avoid common pitfalls.

---

## 1. Commit Related Changes
- A commit should wrap up **one logical set of related changes**.
- Fixing two different bugs should result in **two separate commits**.
- Small, focused commits are easier for teammates to understand and to roll back.
- Use the staging area, including staging only parts of a file, to build granular commits.

## 2. Commit Often
- Frequent commits keep each one small and focused.
- They let you share code with others more often, so integration happens regularly and merge conflicts are less likely.
- Few, large, rarely shared commits make conflicts harder to resolve and history harder to follow.

## 3. Don't Commit Half-Done Work
- Commit only when a piece of work is complete.
- That doesn't mean finishing a whole feature first: split it into logical chunks and commit each when done.
- Don't commit just because it's the end of the day.
- If you only need a clean working copy (to switch branches, pull changes, etc.), use **stash** instead of committing.

## 4. Test Before You Commit
- Don't commit something you merely *think* is finished; test it to make sure it works and has no side effects.
- Untested commits in your local repo are a private matter, but testing matters even more **before pushing or sharing** code.

## 5. Write Good Commit Messages
- Start with a **short summary**, about 50 characters as a guideline.
- Leave a **blank line** between the summary and the body.
- In the body, explain:
  - What was the **motivation** for the change?
  - How does it **differ from the previous implementation**?
- Use the **imperative, present tense** ("change", not "changed" or "changes"), consistent with messages generated by commands like `git merge`.

Example:

```text
Add retry logic to payment client

Transient network errors were failing checkouts. Retry up to three
times with backoff instead of failing on the first timeout.
```

## 6. Version Control Is Not a Backup System
- A remote copy of your files is a nice side effect, but not the purpose.
- Commit **semantically** (related changes together) rather than cramming in whatever files exist.

## 7. Use Branches
- Quick, easy branching was a core requirement of Git from day one.
- Branches keep different lines of development separate.
- Use them extensively: for **new features, bug fixes, experiments, and ideas**.

## 8. Agree on a Workflow
- Git supports many workflows: long-running branches, topic branches, merge vs. rebase, git-flow, and more.
- The right choice depends on your project, your development and deployment process, and (importantly) the team's preferences.
- Whatever you choose, **the whole team must agree on and follow the same workflow**.

---

## Quick checklist

- [ ] One logical change per commit
- [ ] Commit small and often
- [ ] Only commit finished work (use `git stash` otherwise)
- [ ] Test before committing, and especially before pushing
- [ ] Summary ≤ ~50 chars, blank line, body explaining why and how it differs
- [ ] Imperative present tense in messages
- [ ] Don't treat Git as a backup tool
- [ ] Use branches for features, fixes, and experiments
- [ ] Team agrees on a single workflow
